# Doris Multi-Catalog Support

This document describes the multi-catalog behavior added to the Metabase Doris driver, including the decisions made,
the user experience, the implementation details, and the validation scope.

## Goal

The Doris metadata hierarchy has three levels:

```text
catalog -> database/schema -> table
```

Metabase does not expose a separate level for the catalog during table discovery:

```text
schema -> table
```

This change lets a single Metabase database connection synchronize every catalog the Doris user can access. No new
toggle and no new connection field are introduced. The existing **Catalog** field value controls the behavior:

- Catalog empty: all accessible catalogs are synchronized.
- Catalog set: only the named catalog is synchronized.

## User Experience

### Catalog field empty

Metabase Database Explorer does not show a separate catalog-selection screen. The catalog and schema names appear as a
single Metabase schema name:

```text
internal.analytics
internal.reporting
data_lakehouse_db.analytics
data_lakehouse_db.staging
hive_catalog.raw
```

For example, the following Doris hierarchy:

```text
data_lakehouse_db -> analytics -> events
```

appears in Metabase as:

```text
Schema: data_lakehouse_db.analytics
Table:  events
```

### Catalog field set

If the Catalog field is set to `data_lakehouse_db`, the existing single-catalog behavior is preserved:

```text
analytics
staging
```

Schema names are not prefixed with the catalog. This keeps backward compatibility and does not change the metadata
identities of existing single-catalog connections.

## Connection Behavior

Even when the Catalog field is empty, the JDBC connection does not open to a virtual `all` catalog. The connection
keeps using the existing safe startup target:

```text
internal.information_schema
```

Discovery of all catalogs happens after the connection is established, during metadata sync, using `SHOW CATALOGS`.
This avoids writing a sentinel value that does not exist in Doris into the JDBC URL.

## Metadata Sync Flow

When the Catalog field is empty, the driver runs the following flow:

```sql
SHOW CATALOGS;
```

For each visible catalog, it lists the databases/schemas:

```sql
-- internal
SHOW DATABASES;

-- external catalog
SHOW DATABASES FROM `data_lakehouse_db`;
```

For each database/schema, it lists the tables:

```sql
-- internal
SHOW TABLES FROM `analytics`;

-- external catalog
SHOW TABLES FROM `data_lakehouse_db`.`analytics`;
```

In the table metadata returned to Metabase, the schema value is converted to the `catalog.schema` form:

```clojure
{:schema "data_lakehouse_db.analytics"
 :name   "events"}
```

The `__internal_schema` system catalog is not synchronized as user data. The existing system schema filters
(`information_schema`, `__internal_schema`, `mysql`) continue to be applied.

## Column Synchronization

In multi-catalog mode, columns are fetched by parsing the real catalog and schema of each table:

```text
data_lakehouse_db.analytics
          |
          +-> catalog = data_lakehouse_db
          +-> schema  = analytics
```

For an external catalog table:

```sql
SHOW FULL COLUMNS FROM `data_lakehouse_db`.`analytics`.`events`;
```

For an internal catalog table:

```sql
SHOW FULL COLUMNS FROM `orders` FROM `analytics`;
```

The Metabase table identity of each column is recorded again with the combined schema name:

```clojure
{:table-schema "data_lakehouse_db.analytics"
 :table-name   "events"
 :name         "event_id"}
```

This step is required; making only the table list multi-catalog would show the tables in the Explorer but would not be
enough for the Query Builder to find the column metadata.

When a single `internal` catalog is selected, the existing fast `information_schema.columns` batch path is preserved.
When all catalogs are selected, tables are described with `SHOW FULL COLUMNS` to preserve the correct catalog identity.

## Query Builder SQL Generation

Metabase stores `data_lakehouse_db.analytics` as a single schema string. The default MySQL quoting behavior can
produce this incorrectly:

```sql
`data_lakehouse_db.analytics`.`events`
```

Doris expects each identifier part to be quoted separately:

```sql
`data_lakehouse_db`.`analytics`.`events`
```

The driver splits the first part at the first dot, but only for table and field identifiers. As a result, the table
and field references generated by the Query Builder look like this:

```sql
SELECT
  `data_lakehouse_db`.`analytics`.`events`.`event_id`
FROM
  `data_lakehouse_db`.`analytics`.`events`;
```

Other identifier types, such as table aliases, are left unchanged.

Native SQL behavior does not change. The user can write Doris's standard three-part name directly:

```sql
SELECT *
FROM data_lakehouse_db.analytics.events;
```

## Database Filter

If the **Database (optional)** field is empty, all visible databases/schemas in the selected catalog or catalogs are
scanned.

If Catalog is empty and Database is set, the same database name is evaluated as a filter inside every catalog. The
driver first lists the catalog's visible databases; if the specified database does not exist in that catalog, no table
query is run for that catalog.

## Include and Exclude Filters

The existing `Sync Schemas Include` and `Sync Schemas Exclude` fields are applied to the database/schema name, not to
the combined `catalog.schema` name.

Example:

```text
Sync Schemas Include: analytics,reporting
```

In multi-catalog mode this can include the following schemas:

```text
internal.analytics
data_lakehouse_db.analytics
hive_catalog.reporting
```

To filter a specific catalog, that catalog must be entered in the connection's Catalog field.

## Changed Files

### `src/metabase/driver/doris/sync.clj`

- Discovers accessible catalogs with `SHOW CATALOGS`.
- Excludes the system catalog.
- Interprets an empty Catalog field as multi-catalog mode.
- Returns table schema identities in the `catalog.schema` form.
- Splits the combined schema into catalog and database during `describe-table`.
- Maps columns from every catalog to the correct table identity during `describe-fields`.
- Preserves the existing single-catalog behavior when the Catalog field is set.

### `src/metabase/driver/doris/query_processor.clj`

- Converts the `catalog.schema` value into separate catalog and schema parts for table and field HoneySQL
  identifiers.
- Produces correct three/four-part backtick quoting for Doris.
- Leaves existing dot-free schema names unchanged.

### `resources/metabase-plugin.yaml`

- Adds no new toggle and no new field.
- Updates the helper text of the existing Catalog field to describe the "empty = all catalogs, set = selected catalog"
  behavior.
- Clarifies that the Database field can be left empty to sync all visible databases.

### Test files

- Multi-catalog table discovery
- Backward-compatible behavior for a selected catalog
- `catalog.schema` parsing
- Multi-catalog table description and column sync
- Exclusion of the system catalog
- Query Builder table and field identifier quoting
- Dot-free schema names remaining unchanged

## Intentionally Not Done

- No new UI toggle was added.
- Metabase core source code was not changed.
- No new JDBC driver or wrapper was added.
- No special sentinel value is written into the Catalog field.
- The JDBC connection target was not changed for multi-catalog.
- Explorer schema names of single-catalog connections were not changed.

## Limitations

- The separator of the combined schema format is a dot: `catalog.schema`.
- The first dot is treated as the delimiter between catalog and schema. Catalog names that contain a dot are not
  supported by this model.
- In environments with many catalogs and tables, multi-catalog column sync runs more metadata queries than the
  single-`internal`-catalog batch `information_schema` path.
- Visible catalogs and tables are limited by the Doris user's privileges.
- External catalog metadata quality depends on what the relevant Doris connector exposes.

## Validation

Unit tests:

```bash
bash scripts/run-unit-tests.sh
```

All supported Metabase versions:

```bash
for version in 0.59.6.3 0.60.1 0.60.2.2; do
  METABASE_TEST_VERSION="$version" bash scripts/run-unit-tests.sh
done
```

Live validation should at least test the following scenarios:

1. With Catalog empty, `internal` and at least one external catalog appear in the same connection.
2. Two different catalogs with the same schema name appear with separate `catalog.schema` values.
3. Query Builder aggregation and breakout work across both catalogs.
4. When a specific Catalog is entered, only that catalog appears.
5. Include/exclude schema filters are applied across all catalogs.
6. Native SQL works with the three-part table name.
